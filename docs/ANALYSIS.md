# Anatomy of the Microsoft signature package (mpam-fe.exe) and design notes

Документ фиксирует факты, полученные при разборе реального пакета
(01.10.2026): `https://go.microsoft.com/fwlink/?LinkID=121721` →
`https://definitionupdates.microsoft.com/packages/content/mpam-fe.exe?packageType=Signatures&packageVersion=1.459.497.0&arch=x86&engineVersion=1.1.26080.3`,
221 630 376 байт.

## Контейнер

- Внешний файл — PE32 (i386), `e_lfanew = 0xF0`, 5 секций, размер
  optional header 224.
- Весь payload лежит в секции `.rsrc` (raw size 0xD323E00 ≈ 221 МБ).
- Внутри `.rsrc` — CAB-архив (`MSCF` по смещению 0x34714,
  `cbCabinet = 221 393 613`), флаги 0x0000, версии 1.3, 3 папки, 6 файлов.

## Содержимое CAB

| folder | compType | содержимое | размер |
|---|---|---|---|
| 0 | 0x1503 (LZX, окно 2^21) | mpengine.dll, MpSigStub.exe | 16 088 672 + 759 712 |
| 1 | 0x0000 (stored) | mpasbase.vdm | 141 843 400 |
| 2 | 0x0000 (stored) | mpasdlta.vdm, mpavbase.vdm, mpavdlta.vdm | 7 358 416 + 62 575 056 + 3 503 056 |

LZX-папка: 515 CFDATA-блоков (514 × 32768 байт сжатых данных... точнее,
последний блок короткий: 514 × 32768 + 5632 распакованных байт).

## Почему «эвристический» экстрактор не работает

Первый прототип (агентная версия) сканировал файл на сигнатуры `MZ` и
`VDM\x00` и пытался вырезать PE/VDM-блобы по размерам. На реальном пакете это
неработоспособно по построению:

- в 221 МБ данных литеральная пара байтов `MZ` встречается 50 раз (ложные
  срабатывания внутри секций);
- сигнатура `VDM\x00` встречается ровно **1 раз** — второй VDM-блоб
  (`mpasdlta.vdm`) найти таким способом невозможно в принципе;
- настоящая структура — не «блобы», а resource-секция с CAB, у которого файлы
  перечислены в CFFILE по именам.

Правильный путь (реализован в этом репозитории): PE → `.rsrc` → CAB →
CFFILE/CFFOLDER → декодеры STORED / MSZIP / LZX.

## Семантика CAB LZX (по libmspack)

Порт `lzx.go` сделан по `mspack/lzxd.c` (libmspack, LGPL-2.1) — поведение
воспроизведено точно:

1. Битстрим — 16-битные little-endian слова, читаемые от старшего бита к
   младшему (`INJECT_BITS((b1<<8)|b0, 16)` в MSB-режиме).
2. Первые биты потока: 1 бит «есть ли intel filesize» + 32 бита значения —
   используется E8/E9-трансляцией.
3. Деревья: main (256 + 8·slots символов, TABLEBITS 12), length (250, 12),
   pretree (20, 6), aligned (8, 7). Длины кодируются дельтами через pretree
   с кодами-ранами 17/18/19.
4. Количество position slots для окна 2^21 — 50 (`position_slots[11]`).
5. Фреймы по 32768 байт; после каждого фрейма битстрим выравнивается к
   границе 16-битного слова (`REMOVE_BITS(bits_left & 15)`).
6. Uncompressed-блоки: выравнивание сбросом битового буфера, 12 байт
   R0/R1/R2 little-endian, затем сырые данные; нечётная длина блока требует
   пропуска одного байта перед следующим заголовком.
7. Последний фрейм папки может быть короче 32768 — размер папки сообщается
   декодеру до декодирования последнего фрейма (в libmspack это
   `lzxd_set_output_length` при загрузке последнего блока; здесь размер
   известен из CFFILE заранее и передаётся при старте декодирования).
8. E8/E9-трансляция применяется к каждому фрейму, если в main-дереве
   присутствует символ 0xE8 и intel-filesize ≠ 0.

## Верификация

Экстракция реального пакета проверена перекрёстно с `cabextract 1.11`:
SHA-256 всех шести файлов совпали бит-в-бит (см. `TestRealPackageExtraction`
и golden-хэши в `lzx_test.go`, пакет 1.459.497.0 / engine 1.1.26080.3).

## Замечание о совместимости сборок

- Go 1.21+ официально поддерживает только Windows 10+ и линкует PE с
  `MajorOperatingSystemVersion = 10.0` — загрузчик Vista такие файлы
  отвергает.
- Vista-сборки делаются Go 1.20.14 (последняя линия с поддержкой легаси) и
  патчат minOS до 6.00 (`tools/patchpe.py`); Go 1.20 сам ставит 6.0, патч
  нужен для детерминизма и верификации в CI.
- Остаточный риск для реальной Vista: совместимость современного движка
  1.1.26080.x со службой Defender Vista не гарантируется Microsoft; для
  контролируемого обновления используйте `apply -local` с проверенными
  файлами.
