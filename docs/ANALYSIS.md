# Анализ пакетов определений (v2) — измеренная матрица эпох

Все факты получены разбором реальных файлов 01.10.2026. Каждая цифра ниже —
из заголовков самих файлов (PE VS_VERSIONINFO), а не из документации.

## Контейнер (общий для всех эпох)

Пакет = PE32 (i386), весь payload в секции `.rsrc` — один CAB (`MSCF`):
3 папки: LZX-окно 2 МиБ (mpengine.dll + MpSigStub.exe) и две STORED-папки
(mpas*/mpav* .vdm). Схема упаковки не менялась с 2016 по 2026 год.

Каждый `.vdm` — тоже PE-обёртка (MZ → PE32+ → `.rdata` 512 байт + `.rsrc` со
всей базой); версии определений читаются из его VS_VERSIONINFO.

## Ключевые выводы

1. **Поколения определений идут по одной общей шкале времени**:
   1.225 = 04.2016, 1.283 = 12.2018, 1.305 = 10.2019, 1.315 ≈ 2020,
   1.459 = 2026. Из этого следует, что машина пользователя с
   `Definition Version 1.315.1121.0` уже исполняет определения поколения
   ~2020 на движке сборки 2016 года — то есть vdm-формат **обратно
   совместим минимум на 4–5 лет вперёд от сборки движка**.
2. **Линии продуктов разделились**: встроенный Defender (Vista/Win7/8.1,
   KB2267602/KB915597) и MSE-for-XP/Vista — разные потоки. MSE-линия
   (движки 1.2.x) заморожена в 2019–2020; Defender-линия (движки 1.1.x)
   живёт до сих пор (1.1.26080 на Win11).
3. **Конвертация «1.459 → формат 2015» неосуществима как тул**: оба формата —
   закрытые MMPC-контейнеры (PE-обёртка + внутренняя БД движка). Конвертер
   потребовал бы реверса двух БД-форматов и их целостностной модели, а движок
   2016 года не содержит кода для типов записей, добавленных за 10 лет
   (новая техника сканирования = новые структуры в vdm). Честная замена —
   лестница эпох (freshest-first) с health-check и авто-роллбэком.
4. **Проверка «загрузится ли поколение 459 на движке 1.17020» возможна
   только на реальной Vista** — тул делает этот эксперимент безопасным:
   бэкап → GUID-флип → старт службы → наблюдение → авто-роллбэк.
5. Microsoft CDN отдаёт только текущую версию пакета (параметры
   `packageVersion`/`engineVersion` в URL — информационные, любые другие
   значения дают 404). Исторические пакеты — только из архивов
   (archive.org), с пиновкой SHA-256.

## Модель применения (как это делает сама Vista)

- Реестр: `HKLM\SOFTWARE\Microsoft\Windows Defender\Signatures`,
  значения `Antivirus`/`AntiSpyware` (REG_SZ) = имя активной папки
  `...\Windows Defender\Definition Updates\{GUID}`.
- Обновление = новая папка `{новый GUID}` + переключение обоих указателей +
  перезапуск `WinDefend`. Прежний набор копируется в `vdu-backup`.
- v2 воспроизводит ровно эту схему; файлы движка не трогаются
  (режим signatures-only по умолчанию).

## Сборка под Vista

- mingw-w64, `-D_WIN32_WINNT=0x0600`, статическая линковка; minOS 6.00
  задаётся линкером (`--major-os-version 6 --minor-os-version 0`) и
  верифицируется `tools/patchpe.py`. Никакого Go/.NET: один статический exe
  ~170 КБ на x86.
- Скачивание на самой Vista упирается в TLS 1.2 (schannel Vista умеет только
  TLS 1.0) — штатный путь: `fetch` на современной машине → перенос папки →
  `apply -package` на Vista. Прямое скачивание пробуется, но с честным
  сообщением об ошибке TLS.
